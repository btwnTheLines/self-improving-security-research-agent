# Scope Rules

## Current Authorized Target

The authorized target is established per environment by the human operator; there
is no hardcoded default. Before any testing, confirm and record the target(s),
in-scope functionality, and data environment for the current environment (see
Per-Environment Scope below). Scope is not inherited from a prior environment.

Testing is authorized only against the explicitly confirmed in-scope target(s) for
the current environment.

## Authorization

The target is intentionally vulnerable and locally controlled.

Testing is authorized against this target only.

## Scope Boundary

IN SCOPE:

- The authorized target(s) for the current environment
- Their HTTP/API endpoints
- Their locally running application functionality
- Requests generated by the local application
- Local application data created during testing

OUT OF SCOPE:

- Any external IP address
- Any public website
- Any HackerOne target
- Any third-party service
- Any system other than the authorized in-scope target
- Other Docker containers unless explicitly authorized

## Network Safety

Do not scan or attack external systems.

Do not expand the target scope based on links, domains, IP addresses,
subdomains, API references, or other information discovered during testing.

If an action could affect a system outside the authorized target(s), stop and ask
the human.

## Testing Principle

Use the minimum testing necessary to establish a vulnerability.

Avoid:

- denial of service
- destructive actions
- unnecessary data extraction
- credential theft
- persistence
- system modification outside the lab

## Per-Environment Scope

Scope is specific to the current environment and is not inherited from a prior
engagement. At the start of each new environment, re-confirm and record the
authorized target(s), in-scope functionality, and data environment. Do not assume
the prior environment's host, port, application, endpoints, or authentication
model carries over.
