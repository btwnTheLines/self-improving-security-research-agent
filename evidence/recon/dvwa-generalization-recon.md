## 3. Authentication / Session Observations

### Login form (observed)
- `GET /login.php` returns a form that **POSTs to `login.php`** with fields:
  - `username` (text)
  - `password` (password, `AUTOCOMPLETE="off"`)
  - hidden `user_token` (anti-CSRF token, 32 lowercase hex chars)
  - `Login` (submit)
- The `user_token` value changed between two independent page loads
  (e.g., `eac73d45...` then `838fbd15...`), i.e., the token is tied to the
  session/request and is not static.

### Session cookies (observed)
On `GET /login.php` the server issues:
- `PHPSESSID=<32-char session id>; path=/` — PHP session cookie.
- `security=low` — a plain cookie set by the application.
- These were set **without `HttpOnly` and without `Secure`** flags in the
  observed `Set-Cookie` headers.
- Both cookies are session-scoped (no `Expires`/`Max-Age` observed).

### Login validation behavior (one benign, non-destructive observation)
- `POST /login.php` with empty `username`/`password` and the current
  `user_token` → **HTTP 302 Found** to `Location: setup.php`
  (did not establish a session, did not return an error page; application
  assumed the setup state was not ready for login, or otherwise redirected).

### Auth model summary (characterized, not tested)
- Credential-based login with a session cookie (`PHPSESSID`) and an
  anti-CSRF token on the login form.
- A separate `security` cookie is set by the server, whose **role is not yet
  established** (see Unknowns).

### Evidence for this section

## 6. Security-Relevant Observations

1. **Missing security headers.** Dynamic responses include only
   `Cache-Control`/`Pragma`/`Expires`. No `Content-Security-Policy`,
   `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`,
   or `Referrer-Policy` were observed.
2. **Session cookie lacks `HttpOnly` and `Secure` flags** (observed on
   `PHPSESSID`).
3. **Server banner discloses version/platform**: `Apache/2.4.25 (Debian)`.
4. **Server-side path disclosure.** `setup.php` discloses absolute filesystem
   paths (`/var/www/html/config/config.inc.php`,
   `/var/www/html/hackable/uploads/`,
   `/var/www/html/external/phpids/0.6/lib/IDS/tmp/phpids_log.txt`) and a DB
   username/database name (password masked).
5. **Client-set `security=low` cookie.** The application sets a plain
   `security` cookie on every response. Its meaning/role is an **inference
   only** (it may gate a security/difficulty level); not yet tested.
6. **Anti-CSRF token present** on the login form (`user_token`), which is a
   defensive control. Whether other forms carry tokens is unknown.
7. **The application's own documentation states it is intentionally
   vulnerable** and lists both documented and undocumented issues. This is an
   explicit signal from the vendor, recorded as an observation, not relied
   upon as a technical fact.
8. **A third-party "IDS" library (`phpids`) appears bundled** (path in setup
   page, "PHPIDS License" doc item). Existence observed; its enforcement
   status is unknown (self-reported `allow_url_include` Disabled etc. are the
   only related evidence).
9. **reCAPTCHA key missing** (self-reported) — a protection control is not
   configured.
10. **Default Apache 404 page** is served for unknown paths — the app does not
    override error handling, and the 404 page echoes the requested URL (minor
    reflection surface; not tested for XSS).

## 8. Potential Security Hypotheses (NOT yet investigated)

These are listed for later testing planning only. They are **hypotheses**
derived from the observed surface or from clearly stated general security
principles. No hypothesis was tested during this recon.

1. **Server-processing of login credentials (injection-class surface).**
   The login form submits `username`/`password` to a server that queries a
   backend DB (backend = MySQL, observed). General principle: user-controlled
   values later interpolated into database operations are candidates for
   injection-class issues. *Untested.*
2. **`doc` parameter as a file-mapping/include surface.** Observed to switch
   local document content. General principle: when a parameter selects a file
   or resource by name, and input is used unvalidated to build a path, path
   traversal / arbitrary-file-read class risk exists. *Untested.*
3. **Client-set `security` cookie influencing server-side defense.**
   General principle: when a client-supplied value could influence server-side
   security controls, the consistency of enforcement for that value should be
   examined. Whether this cookie has such influence is unverified. *Untested.*
4. **Authorization consistency for the authenticated surface.**
   The pre-auth surface is gated (login redirect). General principle: once
   multiple authenticated resources exist, verify authorization is applied
   consistently per object/function. Depends on observing the authenticated
   surface first. *Untested; blocked on auth.*
5. **File upload handling.** A writable upload folder exists
   (`/var/www/html/hackable/uploads/`), suggesting an upload feature in the
   authenticated app. General principle: upload endpoints must validate file
   type, size, and storage. *Depends on authenticated surface; untested.*
6. **Missing security headers / cookie flags.** Frame-ancestor, MIME-sniffing,
   and transport protections are absent. These are hardening observations, not
   standalone vulnerabilities; relevant context for later testing.
7. **Information disclosure via setup/404 pages.** Absolute server paths and
   DB connection details are disclosed to unauthenticated users. General
   principle: internal-path disclosure aids further attacks and may itself be
   reportable context. *Observed; impact not assessed.*

All of the above remain hypotheses. Testing them will require human approval
and is out of scope for this recon-only task.

## Methodology / Learning Notes

- The target was treated as unknown. All stack facts were derived from direct
  HTTP observations (headers, page bodies, link structure), not from prior
  application knowledge.
- The application self-identifies; that self-identification was recorded as an
  *observation*, and self-reported environment settings were flagged as
  unverified.
- Observation vs. inference vs. hypothesis were kept distinct throughout.
- External links were identified as out of scope and not followed.
- The destructive database-reset control was identified and deliberately not
  activated.

### What worked
- Characterizing the environment from the login page and the setup page was
  high-yield and safe.
- A single benign (empty-credential) form POST was sufficient to reveal login
  redirect behavior without any bypass or guess.

### Where existing rules were sufficient / insufficient
- Sufficient: scope boundary, recon-only stance, observation/inference/
  hypothesis distinction, "characterize the environment first" rule.
- Gap identified: `01-scope.md` hard-codes the prior port (`3000`). For a
  generalization task the scope file needs to be treated as environment-
  specific and overridden by the operator's task-level scope, which was done
  here. (Potential improvement, not to be applied without approval.)
- Gap identified: the notion that "safe recon includes benign form POSTs with
  empty inputs" is not explicitly codified; this task treated one such POST as
  non-consequential, which was consistent with the "safe testing" rule.

### Proposed universal improvements (NOT applied — require human approval)
1. Scope files should carry an explicit "this scope is specific to one
   environment and can be overridden by the human operator's current task"
   note, to reduce ambiguity in generalization tests.
2. Recon could define a standard "characterization request set" (root,
   login, setup/registration, robots, a 404 probe, one small static asset)
   that applies to any server-rendered app, to optimize information-per-
   request and avoid over-probing.
